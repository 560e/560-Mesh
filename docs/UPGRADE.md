# 升级、备份、迁移与回退

已有服务器升级应保留原目录、Compose项目名、公开域名、宿主端口和config/data。不要直接用新模板覆盖原YAML。

## 一致性备份

在原部署目录，选择维护窗口：

~~~sh
umask 077
docker compose stop
tar -czf "../mesh-backup-$(date +%Y%m%d-%H%M%S).tar.gz" config data docker-compose.yml
~~~

备份成功后才继续升级；失败先docker compose start恢复原服务。
备份包含密码相关数据和密钥，私下保存并限制读取。特别要同时保留Headplane数据库、enrollment-vault.key、network-settings和Headscale数据库；不能只复制一个数据库。

## 从源码升级

1. 将新源码拉取/克隆到临时开发目录，检查版本与迁移说明，显式构建一个新标签，例如560-mesh:next。不要覆盖仍供回退的旧标签。
2. 完成上面的停机备份。
3. 在原生产YAML中仅替换image标签，保留域名、账号、端口、挂载与项目名。使用锚点时改一次，服务下直接写image时改initialize和platform两处。
4. 在原部署目录运行docker compose up -d，检查ps -a和logs。
5. 访问原HTTPS域名/adminis/并测试设备、策略、密钥、DNS与路由。

新源码的默认用户隔离会作用于未作互通设置且使用默认全允许策略的安装。自定义/文件策略及明确保存的选择会保留。跨用户互通需求应到“用户与互通”检查，而不是关闭所有访问控制。
数据库与覆盖配置的具体变更应以相应发布说明为准，升级前在测试环境验证。

## 已持有历史离线包

历史560-headscale-platform:1.2.0-dev.2标签仍可在自己的服务器使用。可以docker load导入手头的tar，并在原YAML中填写实际标签。
这不是公共镜像仓库地址，不能假定GitHub已有对应Release附件。历史包可能显示旧品牌；项目源码更名不修改已导入镜像。

## 迁移到另一台服务器

停机备份后，把完整备份、匹配的镜像与原YAML私下复制到新服务器的空目录，恢复并启动。
如需更改宿主端口，只改映射中间值，保留容器3000/8080。手工完成HTTPS入口切换。
不要让新旧两套控制数据库在同一公开入口下并行继续写入。首次使用恢复数据时不要再走空目录初始化替换流程。

## 回退

停止本项目，恢复升级前完整config/data/YAML，再使用保留的原镜像启动。不要只回退镜像而忽略可能不兼容的数据变更。
Nginx、DNS、证书、FRP与防火墙继续由部署者维护。
